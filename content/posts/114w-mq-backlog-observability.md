## 写在前面

某次迭代中，我们对 MQ 消费可靠性做了加固：把消费拆成两阶段——

**MQ 消息先入库，再由异步 Worker 做业务处理。**

改造上线后稳定跑了一段时间，接着又对 Worker 做了一次业务隔离。

隔离上线约 4 天后，一次 inbox 慢 SQL 排查里，我们意外撞上表中约 **114w** 条未完成消息。

可怕的是：服务看起来一切正常，问题却一直在静默。

可观测缺位，让故障藏在「平静」之下——这往往比直接报错更昂贵。

下文按这次事故，试着还原三件事：

1. 我们想做什么？
2. 看似合理的误判是如何发生的？
3. 问题为什么能一直静默？

---

## 1. 我们想做什么

目标很明确：

- 消息不丢
- 可重试
- 并行消费，提高吞吐
- 处理失败可告警、可人工干预

### 1.1 原方案

- **场景 A**：接收 MQ → 入 Redis 队列 → Ack → 业务异步处理
- **场景 B**：接收 MQ → 直接业务处理 → Ack

### 1.2 新方案

```text
接收 MQ → 写入消息表(inbox) → Ack
         → 异步 Worker 并行领取处理
         → 失败则有限次幂等重试
         → 超限进入死信表(dead)并告警
```

### 1.3 inbox 模型与流程

| 字段 | 说明 |
|:--|:--|
| `source` | 业务域 |
| `msgId` | 消息幂等键 |
| `state` | pending（待领取）/ processing（处理中）/ done（已完成） |
| `retry` | 已重试次数 |
| `nextRunAt` | 最早可领取时间（含退避） |
| `lockedBy` | 当前持有该任务的 Worker 标识（完成时必须仍是同一个） |
| `leaseUntil` | 租约到期时间；过期可被其他 Worker 回收 |
| `doneAt` | 成功完成时间 |
| `updatedAt` | 最后更新时间 |
| `lastError` | 最近一次业务失败原因 |

简化流程：

```text
1. MQ 写入 inbox，成功才 Ack

2. Worker 领取（示意）
   SELECT ... WHERE state=pending AND nextRunAt<=now [AND source=?] LIMIT N
   UPDATE ... SET state=processing, lockedBy=me, leaseUntil=...
   WHERE id=? AND <仍可被我抢占的条件>

3. 处理成功
   UPDATE ... SET state=done, doneAt=now, lockedBy=''
   WHERE id=? AND lockedBy=me

4. 处理失败（未超限）
   UPDATE ... SET state=pending, retry=retry+1, nextRunAt=now+退避, lockedBy=''
   WHERE id=? AND lockedBy=me
```

关键契约只有一句：

> 标记 done 时，`lockedBy` 必须还是领取时的那个 `me`。  
> 对不上，完成就不会发生——哪怕业务已经跑过。

这版方案上线后，运行符合预期：能进站、能完成、也能进死信。

### 1.4 业务域隔离

运行中发现：不同业务对时效要求不同。

消息集中时，高时效任务可能被低时效任务拖在同一条领取通道里。于是做了隔离：

> 按业务域拆 Worker，不同 Worker 只领取对应 `source` 的消息，避免互相踩踏。

领取条件从「全局 pending」变成「指定 source 的 pending」。

方案目标正确，也解决了优先级混排的问题。

（实现上还有一处改动，当时没有当成风险点——后文根因处再展开。）

---

## 2. 问题显现与误判

隔离上线约 4 天后，优化 inbox 慢查询时查表，看到一组信号：

| 信号 | 现象 |
|:--|:--|
| pending | 约 114w |
| processing | 约 1w |
| Worker 进程 | 在跑 |
| `MAX(doneAt)` | 停在隔离上线当天 |
| `MAX(updatedAt)` | 还在动 |

### 2.1 第一反应：吞吐不够

`updatedAt` 在变、`doneAt` 不动，还有处理中任务、待领取大量积压。

第一反应是：**Worker 吞吐不够**。

（忽略了 `doneAt` 是「完全不动」，不是「变慢」。）

### 2.2 加并发之后

于是临时把 Worker 数量加了一倍。调整后：

- 上述完成相关信号几乎不变
- 数据库慢请求反而更多

我们把新现象归因成：**Worker 太多，锁竞争加剧**。

此时仍没有意识到：任务处理完后，**完成状态可能根本写不进去**。

### 2.3 后见之明

慢查询、加并发后的库压是真实存在的。

它们解释了「为什么空转很疼」，但解释不了「为什么连续多天几乎没有新的 done」。

**后者才是主矛盾。**

---

## 3. 根因定位

为降低数据库负载，先减了 Worker，问题依旧。

这时才把注意力拉回 `MAX(doneAt)`：它停在上线当天，说明成功完成几乎没有发生。

### 3.1 三条可能

1. Worker 没有领取到任务
2. 业务一直失败
3. 完成状态没有写入成功

逐条对照：

- 存在 processing，且 `updatedAt` 在动 → **不太像 1**
- `lastError` 基本为空 → **不太像 2**
- 剩下重点看 **3**

### 3.2 完成语句与 Worker 标识

完成语句本质是：

```text
UPDATE ... SET state=done, doneAt=now, lockedBy=''
WHERE id=? AND lockedBy=me
```

对比隔离上线前后的实现后发现：Worker 标识从大致

```text
{hostname}-{pid}
```

改成了

```text
{hostname}-{pid}-{source}
```

而库里 `lockedBy` 仍是 **varchar(64)**。

容器环境下 hostname 本身就长，再拼 source，很容易超长；数据库侧静默截断入库，内存里却仍是完整字符串。

核对线上数据：`lockedBy` 长度大量正好是 64，有的已截在业务域名中间。

### 3.3 根因

> 领取时写入的 `lockedBy` 被截断；  
> 完成时用未截断的 `me` 去匹配 → 条件更新失败 →  
> 看起来一直在忙，却交不了卷。

处理也很直接：把 `lockedBy`（Worker ID）改短，保证不超过列宽，并在代码侧守住长度。

发版后，`doneAt` 重新开始前进。

业务域隔离的产品方向没有错；踩雷的是 **参与 CAS 的标识突破了存储契约**，且失败形态是静默的。

---

## 4. 为什么一直在静默

这次的落点不是「终于发现了截断」，而是：

> **完成停了四天，却没有人被信号叫醒。**

### 4.1 可观测缺的是「完成度」，不是「进程正常」

对 inbox 这类「先入库再 Ack」的模型，MQ 侧干净只说明进站成功。至少还需要：

- 按 `source` 的 pending 水位与增速
- 消费/完成速率，以及 `MAX(doneAt)` 新鲜度（是否在滑动窗口内前进）
- 死信增速与典型失败样例
- 更理想：完成/续租类条件更新「命中 0 行」的计数（静默失败探测器）

有进程、有 CPU，不等于消费健康。

`updatedAt` 只能证明记录被处理过；**`doneAt` 才证明完成了处理。**

### 4.2 发布验收停在了「起来了」

隔离这类会改领取语义、持有者格式的变更，上线后应持续看：成功完成是否还在发生，而不是只看进程存活。

若上线当天就盯一眼 `MAX(doneAt)`，不必等慢 SQL 和 114w。

### 4.3 列宽是契约

凡写入后还要拿来做等值匹配的字段（锁、租约、幂等键），长度与格式变更都应进评审检查项：

- 能否截断？
- 截断后行为是什么？
- 有没有单测 / 断言？

这不是「记性不好」，是契约没产品化。

### 4.4 排障要优先关键信号

吞吐、锁竞争都是常见且「看起来合理」的归因；缺的是一条更靠前的检查：

> 完成时间还在前进吗？不动，先别加并发。

误判不可耻；没有把「完成新鲜度」放在第一信号位，才会让放大器（加 Worker）先上场。

---

## 5. 结语

114w 是结果。

真正的代价是：完成已经停了，系统仍显得忙碌，而我们用了四天，才在慢查询里看见问题。

我们把「不丢消息」做成了，却没有把「完成工作」的可见性做到位。

> 可观测能力缺失的代价，往往不是当下炸一次，而是在静默中堆高问题风险。
